# ADR-0018: 座舱视觉设计系统与人机工效规范

- 日期：2026-10-22
- 状态：已采纳

## 背景

CarWeb 经过多轮底层通信与流媒体协议演进（如 ADR-0017 支持 scrcpy 4.0 flex display、虚拟屏无感尺寸自适应），核心链路趋于稳定。但在前端呈现层：
1. UI 样式散落着十六进制颜色硬编码（如 `#94a3b8`、`#1e293b`），缺乏统一的语义化 Design Tokens；
2. 缺乏针对车载/座舱弱光、强光及震动环境的人机工效硬门禁（例如触控目标尺寸随意）；
3. 后续引入 AI Agent 协助编写新视图时，容易被第三方通用模板带偏，退化出不契合车机特性的设计风格（如过小的鼠标按钮、高饱和刺眼紫蓝渐变等）。

## 决策

结合业内高度认可的权威标准与 CarWeb 本地技术栈特征，确立 CarWeb 专属的视觉设计规范与工程审查准则：

### 1. 行业标准依托
- **AAOS (Android Automotive OS) & ISO 15008 / NHTSA**：确立车机交互硬约束。核心可交互元素物理靶区强制 $\ge 48\times 48\text{px}$，间距 $\ge 8\text{px}$；字体建立严密阶梯；深色模式避免纯黑刺眼反光。
- **W3C DTCG (Design Tokens Community Group)**：建立语义化 Token 体系（`surface.*`、`text.*`、`accent.*`），将样式配置与业务逻辑解耦，杜绝裸色值。
- **shadcn/ui 自主代码权理念**：不引入大型第三方 UI 黑盒，坚持本地原子化组件，通过 `tailwind-merge` + `clsx` 实现高内聚、易测试的组件实现。

### 2. 规范在工程体系中的落地
- 在根目录设立 `CODING_STANDARDS.md`，使 Matt Pocock 的 `/code-review` 能够自动执行 UI 与人机工效的审查；
- 扩展 `tailwind.config.js`，注入标准语义 Tokens；
- 补充组件尺寸与可访问性自动化测试（Vitest 单元测试切面），将规范从“口头约定”上升为“CI 自动拦截”。

## 影响与后果

- **正面影响**：
  - 彻底终结前端组件样式杂乱硬编码现象；
  - 提升在真机、车机车机大屏及颠簸场景下的防误触率与易用性；
  - 让后续所有由 AI Agent 开发的前端界面保持统一的高水准审美与一致性。
- **负面影响/代价**：
  - 开发新组件时必须遵循 48px 触控区与语义 Token 规范，稍微增加了编写微小控件时的结构考虑（需包裹透明 padding 容器）。
