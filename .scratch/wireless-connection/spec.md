# Spec: 工业级纯无线连接（官方 ADB 宿主守护与免物理线配对）

> 状态：**ready-for-agent**  
> 标签：`ready-for-agent`

---

## Problem Statement

CarWeb 目前的有线 USB 连接运行稳定，但在真实的座舱用车场景中，要求用户必须随身携带 USB 数据线并在狭小车舱内走线插入，极大地损伤了使用体验与便捷度；部分车机的 USB 接口更被行车记录仪或车载外设独占，导致无法使用虚拟屏。

前期曾尝试在轻量代理内纯手工复刻 Android 11+ 的 SPAKE2 与 TLS 配对协议，但由于密码学依赖不可解析且缺少对连接期 TLS 1.3 证书握手的支持，导致整条无线链路在原理层面无法闭环。用户迫切需要一种**无需任何物理 USB 数据线**、**无需在手机安装任何侵入性 App**、且能**完全保留独立虚拟屏分屏与系统级触控**的商用级纯无线连接体验。

---

## Solution

采用工业标准的**车机官方 ADB 宿主守护进程 + 浏览器标准协议对接**架构：

1. **宿主层（Host Daemon）**：
   在车机端后台直接部署并常驻运行 Google 官方的 Android SDK `adb` 二进制程序（约 5MB 单文件，原生完整支持 Android 11+ 的无线配对与连接协议），监听本地标准管理端口（`127.0.0.1:5037`）。彻底废弃易碎的自研 SPAKE2/TLS 密码学代理。

2. **通信层（Daemon-to-Browser Transport）**：
   车机本地提供一个极简的本地协议网桥，将宿主 `5037` 端口的安全字节流暴露给车机浏览器；浏览器端通过标准 ADB Server 客户端协议与其通信。

3. **用户配对与连接流程（Zero-Cable Wireless Onboarding）**：
   - 用户上车，手机接入车载局域网（车机 WiFi 热点或手机热点）。
   - 手机在系统「开发者选项 → 无线调试」中开启配对码或二维码。
   - 车机界面提供配对码输入与二维码解析，触发宿主 `adb pair` 完成秒级安全握手。
   - 配对成功后宿主自动 `adb connect`，浏览器检测到设备上线，立即通过现有会话层无缝创建独立虚拟屏与分屏桌面。
   - 后续上车只要连入同一局域网，系统自动识别并一键免配对重连。

4. **架构保全**：
   独立虚拟屏（Virtual Display）、`scrcpy 4.0` 协议扩展、WebCodecs 硬解、双开分屏桌面、音频捕获与触控注入链路保持 100% 原样复用，无任何破坏性重构。

## User Stories

1. 作为车主，我进入车内时即使手头没有任何 USB 数据线，我也希望直接将手机无线连接到车机，以便无需繁琐插线即可使用大屏导航与多任务。
2. 作为车主，我希望在手机已连接车载 WiFi 时，无需在手机上额外下载和安装任何第三方 App，以便保障手机安全与系统纯净。
3. 作为车主，当我首次进行无线连接时，我希望能在车机屏幕上清晰看到配对指引，以便顺畅开启手机的无线调试配对码。
4. 作为车主，我希望可以直接在车机屏幕上输入手机显示的 6 位配对码与配对端口号，以便在 1 秒内完成车机与手机的初始安全配对。
5. 作为车主，我希望如果车机配备了摄像头或支持外置扫码，我可以直接扫描手机无线调试界面展示的二维码，以便免去手动敲入端口与数字的操作。
6. 作为车主，当配对成功后，我希望车机能够自动发起 ADB 连接并启动虚拟屏，以便无需我再次手动点击连接按钮。
7. 作为车主，在无线投屏运行期间，我希望车机屏幕呈现的是完全独立的虚拟屏（支持左右分屏双开应用），手机端可以熄屏或回复聊天，以便两者互不干扰。
8. 作为车主，在无线投屏运行期间，我希望车机上的触控点击与滑动能获得接近有线连接的毫秒级流畅响应，以便操作地图和应用丝滑不卡顿。
9. 作为车主，在无线投屏运行期间，我希望整车音频能够由专用音频链路独占传输，以便在车内音响中获得清晰无损的导航与音乐声音。
10. 作为车主，当我第二次上车且手机再次连入车机热点时，我希望车机自动识别到已知手机并自动重新连接，以便无需每次上车重复扫码配对。
11. 作为车主，如果车内存在多台已配对过的家庭成员手机，我希望在车机连接列表中看到清晰的设备历史并能手动挑选，以便随时切换投屏源。
12. 作为车主，如果我在使用过程中暂时离开车辆导致 WiFi 信号中断，我希望车机界面明确展示“网络重连中”提示，并在我返回信号范围内时由链路监督模块自动恢复虚拟屏会话，以便画面与音频无缝续播。
13. 作为车主，如果我主动在手机端关闭了无线调试，我希望车机能友好提示“手机无线调试已关闭”，以便我知道如何恢复连接。
14. 作为车主，我希望可以在车机上随时点击“忘记此设备”，以便清除该手机的连接记忆与配对缓存。
15. 作为开发者，我希望无线连接的前端业务逻辑与宿主 ADB 进程之间具备明确的依赖注入测试接缝，以便在没有真实车机与手机的环境下通过自动化单元测试 100% 覆盖状态机转换与异常边界。

## Implementation Decisions

### 1. 宿主端架构重构（废弃自研密码学，收敛为官方 ADB 守护服务）
- 彻底废除旧有的自研单文件 SPAKE2 代理。
- 车机宿主后台直接依赖官方预编译的 Android SDK `adb` 守护程序。
- 宿主后台仅维护极简的进程监控与通信管道，将本地标准管理端口（`127.0.0.1:5037`）桥接至浏览器可访问的 WebSocket 安全通道，严禁在应用层自行逆向或实现 TLS/SPAKE2 等底层握手算法。

### 2. 浏览器端连接层重构（对齐标准 ADB Server 协议）
- 前端连接层引入 ADB Server 协议客户端，替代旧有的直连 TCP 虚拟设备实现。
- 提供统一的连接管理接口，涵盖四大核心操作：
  - `pairDevice(host, port, code)`：调用官方 ADB 协议的配对指令。
  - `connectDevice(host, port)`：调用官方 ADB 协议的建连指令。
  - `listDevices()`：实时获取当前宿主挂载的设备列表与在线状态。
  - `openTransport(serial)`：从宿主获取针对指定设备的双向数据流通道。
- 建立的数据流通道直接适配为既有的标准数据包流，与会话管理层完全无缝对接。

### 3. 连接状态机与链路监督适配
- 保持既有的五态连接模型（`idle / connecting / connected / disconnected / error`）不变。
- 无线连接断线检测与重连逻辑深度接入链路监督器（LinkSupervisor）：
  - 区分“WiFi 传输链路闪断”与“用户主动断开”。
  - 遇到短时掉线时触发自动重试退避序列，重连时严格保留既有虚拟屏几何配置与显示模式。

### 4. 界面交互优化（ConnectionOverlay 改造）
- 界面上的无线连接模块重构为两阶段引导流：
  - **初次连接**：提供「输入配对码」与「扫码配对」两套输入入口，附带简明的系统路径指引动画。
  - **日常重连**：直接展示已配对设备卡片与局域网在线设备，提供“一键连接”与自动重连开关。
- 彻底清理当前界面中无法工作的旧网络拓扑手动推测逻辑，改为由宿主自动报告探测结果。

## Testing Decisions

### 测试原则
- **只测外部行为，不测实现细节**：测试关注状态机在不同网络事件与操作下的状态迁移动作、错误提示与重连调度，不依赖内部数据传输格式。
- **高阶单一接缝原则（Single High Seam）**：统一在连接管理服务接口处设置依赖注入接缝，所有测试通过注入 Mock 客户端完成。

### 测试范围与模块
1. **无线配对与建连控制器**：
   - 验证正确输入配对码时触发 `pair -> connect -> startSession` 链路。
   - 验证配对超时、配对码错误、网络不可达时的降级与错误展示。
   - 参考既有的连接层单元测试（如 USB 重试与断线测试模式）。
2. **已记住设备自动重连**：
   - 验证页面刷新或掉线重入时，从设备记忆中读取目标地址并自动发起重新连接。
   - 验证连续多次重试失败后优雅降级至手动连接面板。
3. **断开意图隔离**：
   - 验证用户主动点击“断开”或页面卸载时标记有意断开，不会误触发异常重连弹窗。

## Out of Scope

1. **Android 10 及更早旧版本的免线配对**：Android 10 及更老旧系统底层不支持无线调试扫码配对机制，不在本项目纯无线免物理线支持范围内。
2. **手机端独立投屏 App**：本项目不开发、不分发任何手机端投屏应用，严格基于系统原生能力保障独立虚拟屏与系统级触控。
3. **Miracast / DLNA 协议支持**：不实现消费级电视盒子类的只读同屏广播协议。
4. **公网远程穿透投屏**：仅支持车内局域网（车机热点或手机热点）环境，不提供跨公网远程连接。

---

## Further Notes

- **系统资源消耗**：官方 `adb` 守护程序在车机空闲时仅占用约 5~8MB 内存，CPU 占用近乎为零，远低于自研代理可能存在的内存泄漏风险。
- **版本向前兼容性**：依托官方 ADB 守护程序，未来 Android 16/17 即使微调无线调试协议细节，只需升级车机端对应的官方二进制即可，前端代码与协议实现完全不受波及。
